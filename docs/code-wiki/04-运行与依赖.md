# 运行与依赖

## 1. 先说结论

基于当前工作区文件，主 TypeScript 系统的“完整官方运行方式”不能被完全恢复；原因不是分析不足，而是仓库本身缺少标准依赖清单和构建声明。

当前能够确认的，和不能确认的，应严格分开。

## 2. 已确认的信息

### 2.1 主系统是 JS/TS CLI 运行时

从源码可确认：

- 主体语言是 TypeScript / TSX
- 明确使用了 `react`
- 使用了 `@commander-js/extra-typings`
- 使用了 `bun:bundle`
- 使用了 `lodash-es`
- 使用了 `zod`
- 使用了 `@modelcontextprotocol/sdk`

这说明主系统是一个基于 JS 运行时的 CLI/TUI 工程，并且明显兼容 Bun 构建特性。

### 2.2 使用了 Bun 特性

多处源码直接导入：

- `feature` from `bun:bundle`

这意味着：

- 构建时存在 dead code elimination / feature flag 裁剪
- 运行时或构建时至少部分依赖 Bun 能力

### 2.3 主系统存在多种运行模式

从 `entrypoints/cli.tsx` 和 `main.tsx` 可以确认支持：

- 普通交互式 CLI
- 非交互 `--print`
- MCP server
- remote-control / bridge
- daemon
- 背景 session 管理

### 2.4 主系统联网依赖明确存在

从 `utils/preflightChecks.tsx` 等代码路径可以确认，系统会检查 API / OAuth 端点连通性。

因此主系统不是纯本地离线工具，至少以下能力依赖网络：

- 模型 API
- OAuth / 登录
- 部分远程控制与 bridge 能力

## 5. 主系统可还原的运行方式

以下是“基于源码入口能确认的运行路径”，注意这不是完整的一键启动说明，而是运行模式说明。

### 5.1 普通 CLI 路径

入口：

- `entrypoints/cli.tsx`

主链：

```text
entrypoints/cli.tsx
  -> main.tsx main()
  -> run()
  -> init()
  -> 命令 / 工具装配
  -> REPL 或非交互执行
```

### 5.2 MCP server 路径

入口：

- `entrypoints/mcp.ts`

能力：

- 列出内部工具
- 调用内部工具
- 通过 stdio 提供 MCP server

### 5.3 remote-control / bridge 路径

入口参数：

- `remote-control`
- `rc`
- `remote`
- `sync`
- `bridge`

行为：

- 启用 bridge 环境
- 做登录、策略与版本检查
- 进入 `bridgeMain()`

### 5.4 daemon 路径

入口参数：

- `daemon`
- `--daemon-worker`

行为：

- 启动长生命周期 supervisor 或 worker

### 5.5 背景 session 路径

入口参数：

- `ps`
- `logs`
- `attach`
- `kill`
- `--bg`
- `--background`

行为：

- 管理背景会话注册与访问

## 7. 主系统运行前提

从源码证据推断，运行主系统至少需要满足：

1. JS 运行时
   - 且很可能需要兼容 Bun 特性

2. 终端环境
   - 交互式模式依赖 TTY

3. 网络访问
   - API / OAuth / 远程控制路径需要网络

4. 认证信息
   - 某些路径需要登录或 token

5. 项目配置
   - settings、policy、plugin、MCP 相关配置会参与启动

## 9. 风险与注意事项

### 9.1 对主系统

- 当前无法保证直接在本地启动成功，因为缺少 manifest 与构建脚本。
- 任何“执行 `npm install` / `bun install` / `pnpm dev`”的建议都属于猜测，不应伪装成已验证事实。

### 9.2 对 Python 子项目

- 依赖外网下载 Binance 数据
- `data/` 目录未提交到仓库，需要自行准备
- 结果受数据区间和参数设置影响
